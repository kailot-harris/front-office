# Phase 0a — Vendor-Level Data Source Verification (MLB)

**Scope**: Direct, live verification of the raw vendor APIs/sites underlying the MLB Analytics data
pipeline, per GitHub issue #3 and `docs/PHASE0_RESEARCH_PLAN.md` §2. This checks the *raw* source
behind each R-package wrapper (issue #2's territory), since a wrapper's claimed coverage can lag the
live API. All claims below are tied to a live fetch/search performed on **2026-10-17**.

**Non-goal**: this file does not assemble or edit `docs/MLB_REPLICATION_PLAN.md`. It is raw research
input for a later assembly step.

## Findings table

|---|---|---|---|---|
| **MLB Stats API** (`statsapi.mlb.com`) | Live schedule endpoint, base URL shape, auth model | Base URL `https://statsapi.mlb.com/api/v1/`. `GET /schedule?sportId=1&date=YYYY-MM-DD` returned a live, successful, **unauthenticated** response for 2026-10-17 (an ALCS playoff date): root metadata (copyright, totalItems/totalGames) + `dates[].games[]` array with `gamePk`, `gameType`, `season`, `status`, `teams.{away,home}`, `venue`, `series` fields. Response is marked `"publicFacing":true`. No rate-limit headers were present in the response body (none observed, not necessarily none enforced — rate limits are not published in a public rate-limit doc). Other live endpoints confirmed to exist via community docs: `/teams`, `/teams/{teamId}/roster`, `/game/{gamePk}/boxscore`. MLB also operates a partner-gated official doc site at `docs.statsapi.mlb.com` behind MLB's identity provider — the public `v1` surface used by `baseballr`/community tools is a separate, unauthenticated, undocumented-but-stable surface. | 2026-10-17 | `https://statsapi.mlb.com/api/v1/schedule?sportId=1&date=2026-10-17` (live fetch); endpoint catalog cross-check: `https://github.com/toddrob99/MLB-StatsAPI/wiki/Endpoints` |
| **Baseball Savant** (`baseballsavant.mlb.com`) | Statcast pitch-level fields, bulk CSV search endpoint shape, coverage start year | Bulk download is `GET https://baseballsavant.mlb.com/statcast_search/csv?...` with query params (`hfPT`, `hfAB`, `hfBBT`, `hfZ`, `hfSea`, date ranges, team/player filters, `all=true`) producing a pitch-by-pitch CSV. Official field-reference page (`csv-docs`) confirms exit velocity, launch angle, barrel classification, and Statcast-tracked spin rate (`release_spin`) are present fields. **Coverage-year nuance** (do not assume "2015" — the doc's own wording differs from the commonly-repeated figure): the live doc states *"Values from 2008-16 are via PitchFX, and adjusted to roughly out-of-hand release point. All velocities from 2017 and beyond are Statcast, which are reported out-of-hand."* This means the raw CSV spans back to 2008 (PITCHf/x-era, non-Statcast) with a methodology seam at 2017 for velocity fields specifically — a researcher should not treat "2015" (the commonly cited stadium-rollout year) as the field's own stated coverage boundary without separately checking each metric family (batted-ball fields vs. pitch-velocity fields may have different seams). The doc also flags a 2026-specific definitional change: strike-zone reference point moved from front-of-plate (through 2025) to middle-of-plate in 2026 to align with the ABS (Automated Ball-Strike) system — relevant if any zone-based feature engineering spans the 2025/2026 boundary. | 2026-10-17 | `https://baseballsavant.mlb.com/csv-docs` (live fetch, field reference) |
| **FanGraphs** | Advanced-stat (wOBA, wRC+, FIP, xFIP, SIERA, WAR) source/scraping ToS constraints | FanGraphs' live Terms of Service (`/about/terms-of-service`) contains **no explicit anti-scraping/robots clause**, but Section 6 (Member Conduct) prohibits accessing "the Service by any means other than through the interface that is provided by FanGraphs," and Section 17 (Proprietary Rights) prohibits reproducing, duplicating, copying, reselling, or creating derivative works from "any portion of the Service," plus a broader "not to modify, rent, lease, loan, sell, distribute" clause. Net effect: programmatic scraping of FanGraphs pages is not explicitly named but is plausibly captured by these broad restrictions — **ToS risk, not a clean green light**, consistent with why `baseballr`'s FanGraphs wrapper functions (per issue #2's territory) are the safer sanctioned path versus raw scraping. A FanGraphs engineering blog post ("The State of FanGraphs 2026") separately notes the site estimates ≥60% of its traffic is non-human (bots/crawlers/AI scrapers), i.e. FanGraphs is actively aware of and concerned about scraping load — supporting a bias toward wrapper-mediated, rate-limited access rather than direct scraping in any future pipeline. | 2026-10-17 | `https://www.fangraphs.com/about/terms-of-service` (live fetch); `https://blogs.fangraphs.com/the-state-of-fangraphs-2026/` (search result, title/date corroboration) |
| **ESPN injuries feed — MLB** (`site.web.api.espn.com`, `baseball/mlb` segment) | Confirm/deny the `athlete.id`-missing / Player-Card-href-parsing quirk already confirmed for NFL/WNBA/NBA | **Confirmed via live fetch — the same quirk carries over to MLB, verified directly rather than assumed.** `GET https://site.web.api.espn.com/apis/site/v2/sports/baseball/mlb/injuries` returns live JSON where each injury entry's `athlete` object has `firstName`, `lastName`, `displayName`, `shortName`, `links`, `headshot`, `position`, `team` — **no direct `id` field on the athlete object itself**. The player's numeric MLB-context ID must be parsed out of the `links` array's `playercard` entry, e.g.: `{"rel":["playercard","desktop","athlete"],"href":"https://www.espn.com/mlb/player/_/id/39878", "text":"Player Card", ...}` (observed example: Corbin Burnes → id `39878`, parsed from the href path segment, not a JSON field). So: same join strategy required as NFL/WNBA/NBA — regex/split the trailing path segment of the `playercard`-rel link's `href` to recover the athlete ID for joining to other ESPN/roster data. | 2026-10-17 | `https://site.web.api.espn.com/apis/site/v2/sports/baseball/mlb/injuries` (live fetch, response body inspected) |
| **The Odds API** | MLB sport key, player-prop market-key conventions, whether player props use the same event-odds endpoint pattern as NFL/WNBA | Sport key confirmed as **`baseball_mlb`** (matches the issue's expectation). Player-prop market keys follow the documented `{batter|pitcher}_{stat}` convention, confirmed examples: `batter_hits`, `batter_home_runs`, `batter_doubles`, `batter_hits_runs_rbis`, `batter_strikeouts`, `pitcher_strikeouts`, `pitcher_record_a_win`, `pitcher_hits_allowed`, `pitcher_outs`, `pitcher_earned_runs`. Endpoint pattern: **confirmed same two-tier pattern as NFL/WNBA** — featured markets (moneyline/spreads/totals) are queryable from the bulk `GET /v4/sports/baseball_mlb/odds` endpoint across many games at once, while player props and other additional markets require the **per-event** `GET /v4/sports/baseball_mlb/events/{eventId}/odds` endpoint, queried one game at a time (the official docs state the event-odds endpoint "will only query one event at a time" given response-size volume). Docs also note non-featured-market (prop) coverage is "currently limited to selected bookmakers and sports, and expanding over time" — i.e. prop-market coverage completeness should not be assumed uniform across all MLB games/books. No account was created and no API key was used; all of the above was verified from The Odds API's public documentation pages only. | 2026-10-17 | `https://the-odds-api.com/sports/mlb-odds.html` (live fetch); `https://the-odds-api.com/liveapi/guides/v4/` (live fetch); `https://the-odds-api.com/sports-odds-data/betting-markets.html` (search result, market-key list corroboration) |
